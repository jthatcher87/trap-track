# Trap Track · PNiXStudio

A standalone, installable web journal that teaches TRAP → TRAC, helps someone reflect on an event, and turns that reflection into a next-time plan. No build step or runtime framework. GitHub Pages serves `app/`; each individual owns their own private Google Sheet and Apps Script deployment.

## Current delivery status

Implementation and local verification are complete as recorded in TESTING.md. GitHub repository creation/Pages activation and live Google Apps Script authorization/deployment require the account owner's sign-in. No live hosted URL or end-to-end cloud verification is claimed.

## Features

- Learn: framework, worked example, safe use, sources, and rehearsal guidance.
- Reflect: five-step editable journal, optional prompts, before/start/peak/after mood checks, multiple emotions, own vocabulary, 0–10 intensity, mixed-emotion exploration.
- Plan: desired outcome, early cue, alternative coping, if–then response, support, and follow-up.
- Review: local search and plan rehearsal; update or delete entries.
- Personalize: Cyber Cyan / Neon Purple atmosphere and shorter writing spaces.
- Privacy: browser-side AES-256-GCM with PBKDF2-SHA256 (310,000 iterations), unique random salt and IV per save, passphrase and Sheet access token in memory only. No analytics or external AI.
- Back up: encrypted export/restore with merge and deletion markers.
- Sync: explicit, acknowledged Google Sheets read/merge/write with revision conflict protection. Not a fire-and-forget POST. A private Apps Script iframe bridge avoids a cross-origin JSONP endpoint or blind no-CORS writes.
- Offline: local fonts, Font Awesome icons, app shell, journal editing, and backups. Sync needs Internet. Install requires HTTPS and a compatible browser.

## GitHub Pages deployment

1. Create `trap-track` in the intended GitHub account. Put the contents of this directory at the repository root, retaining the `.github` directory.
2. Use a `main` branch. In Settings → Pages → Build and deployment, choose **GitHub Actions**. GitHub plan and repository visibility determine Pages availability; never add personal records or secrets to the repository.
3. Push to `main` or run **Test and deploy GitHub Pages** manually.
4. Wait for the workflow to succeed; use the URL returned by the deployment. No absolute asset paths are used, so a repository subpath works.
5. Open the app over HTTPS. On Android, use the browser's install/Add to home screen action. On iOS, Safari → Share → Add to Home Screen. Browser behavior varies.

Local development: serve `app/` through a static server on localhost. `npm run check` and `npm test` use Node 22+ without package installation.

## Google Sheets + Apps Script setup (one person per deployment)

1. Create a new standalone project at https://script.google.com/ under the journal owner's account.
2. Replace its code with `gas/Code.gs`. Add an HTML file named **Bridge** using `gas/Bridge.html`. In Project Settings, enable manifest editing and use `gas/appsscript.json`.
3. Run `setup()` once and authorize the spreadsheet scope. This creates a private spreadsheet named **Trap Track · Private encrypted journal**. It also generates a private access token in Script Properties. Running setup again reuses the existing Sheet and token.
4. In Project Settings → Script Properties, set `ALLOWED_ORIGIN` to your app's HTTPS **origin**, e.g. `https://jthatcher87.github.io`, without a repository path or trailing slash. `SHEET_ID` and `ACCESS_TOKEN` are generated by setup. Open the Sheet from its ID if needed. Never commit these values or paste the token into chat.
5. Deploy → New deployment → Web app. Execute as **Me**. The iframe bridge must be accessible without an interactive Google login, so use **Anyone** where the account permits it. This exposes the bridge, not journal contents: read/write requires the generated high-entropy token, and records are encrypted before leaving the app. If organizational policy forbids this deployment type, stop; use local-only journaling until an authenticated backend is provided.
6. Copy the deployed `/exec` URL. In the app's Settings, enter the URL and private access token. Connect; the app verifies the token with a read request.
7. Create/unlock the journal with a unique passphrase of 12+ characters. Keep a recovery copy of that passphrase yourself; the app cannot recover it.
8. Save an entry, then My journal → Sync with my Sheet. A success message means the backend acknowledged the write. The Sheet's Vault tab stores revision, update time, encrypted chunks, and format. Journal prose is intentionally not readable in Sheet cells.
9. On a second device, use the same passphrase, endpoint, and token, then sync. Forgetting the passphrase makes existing ciphertext unreadable. A wrong passphrase aborts sync before any remote write.
10. When code changes, update the deployment version in Apps Script; do not use a `/dev` URL.

## Privacy and operational limits

- Local encrypted records persist in browser storage. Clearing site data can delete them. Export encrypted backups regularly. Unsaved drafts are memory-only and lost on reload/closing/locking.
- Lock before leaving a shared device. An unlocked page exposes plaintext. This release has manual locking, not biometric locking or automatic background locking.
- The passphrase is not transmitted; the separate access token goes only to your deployment. The token authorizes ciphertext reads and writes. Anyone with that token can download, replace, or delete ciphertext, even without decrypting it. Revoke/rotate it in Script Properties if exposed.
- `ALLOWED_ORIGIN` permits one origin. GitHub Pages repository paths share an origin; it does not isolate one repository from other content on that account's Pages origin. A dedicated custom domain provides a tighter boundary. No secrets appear in URLs.
- Google sees account metadata, timestamps, ciphertext length, and encrypted data; Google retention/version history may retain older snapshots. Sheet sharing is controlled by its owner. Deletion markers propagate logical deletion, not secure erasure from backups/history.
- Sync explicitly merges records by most recent device timestamp; keep device clocks accurate. Concurrent edits to the same record use the latest timestamp, not field-level merging. Backend revision checking prevents overwriting a snapshot changed between read and write; repeat sync after a conflict.
- Backend limits encrypted snapshots to 1.5 MB and chunks cells below 40,000 characters. Google service quotas and browser storage limits also apply. This is an individual journal, not a multi-tenant clinical records system.
- The iframe bridge uses strict origins, a random per-session readiness nonce, and request IDs. Live Apps Script embedding, organization access policies, and mobile installation remain deployment acceptance checks.
- Educational reflection, not diagnosis or treatment. TRAP/TRAC originates in behavioral activation. DBT-informed ideas are complementary. Emotion combinations are suggestions, not objective decomposition. Protective boundaries and needed rest are not automatically avoidance.
